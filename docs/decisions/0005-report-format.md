# ADR 0005: Формат структурированного отчёта

- Статус: proposed
- Дата: 2026-09-02
- Владельцы: инженерная команда, клиническая команда

## Контекст

`docs/windows/README.md` описывает экран отчёта с предварительным просмотром и экспортом обезличенного/клинического варианта по роли. `docs/security/README.md` требует, чтобы отчёт различал исходные данные, вычисленный результат и ручной комментарий, а `docs/architecture/README.md` — чтобы результат был воспроизводим для одного model package и одного входа. PACS-интеграция (включая DICOM SR) явно отложена до появления локального файлового MVP.

Нужен формат, который одновременно: машинно проверяем в тестах и регрессиях, читаем врачом, и не превращает исследовательские метрики в видимость клинического заключения.

## Решение

**Двухслойный отчёт с единственным источником истины:**

1. **Канонический слой — JSON** (`report.schema.json`, версионированная схема). Он и только он является результатом анализа: признаки с именем, версией определения, значением, единицей, флагом качества и допустимым диапазоном; вероятности и неопределённость; статус QC/OOD; версии model package, предобработки и label map; commit SHA приложения; идентификаторы серий (псевдонимные); ручные комментарии врача — в отдельной секции с указанием автора и времени.
2. **Человекочитаемый слой — PDF/A**, генерируемый **детерминированно из JSON**. Никакие значения не вычисляются на этапе рендеринга; PDF не может содержать того, чего нет в JSON.

**Два варианта экспорта по роли:**

- *клинический* — с идентификаторами пациента, восстанавливаемыми из внешнего защищённого реестра, для локального использования в организации;
- *обезличенный* — только псевдонимные идентификаторы, пригоден для передачи и разбора случаев.

Разграничение выполняется на уровне сценария `Application` и фиксируется в аудите; PDF-рендерер не решает, что скрывать.

**Обязательные элементы обоих вариантов:** версия model package и её статус подписи, факт и причина отказа QC/OOD (если был), явная формулировка ограничений («вспомогательный инструмент, не автономная диагностика»), визуальные оверлеи масок, на которых основаны измерения.

**DICOM SR** — отложен вместе с PACS-интеграцией; при её появлении SR генерируется из того же JSON как третий слой представления, без параллельной логики вычислений.

## Рассмотренные варианты

- **Сразу DICOM SR как канонический формат** — отклонено: связывает MVP с PACS-стеком до того, как локальный файловый сценарий отработан; сложнее тестировать и версионировать схему признаков проекта.
- **Только PDF** — отклонено: непригоден для регрессионных тестов, сравнения версий модели и анализа ошибок; из PDF нельзя надёжно извлечь численные признаки обратно.
- **HTML вместо PDF/A** — отклонено для клинического экспорта: слабее гарантии долговременной неизменности отображения; HTML остаётся допустимым для предпросмотра внутри приложения.
- **FHIR DiagnosticReport** — отклонено на MVP: требует развёрнутого FHIR-контура и терминологического маппинга; рассматривается вместе с интеграцией в МИС отдельным ADR.
- **Единый отчёт с ролевым скрытием при просмотре** — отклонено: PHI не должна попадать в файл, который может быть передан вовне; фильтрация выполняется при экспорте, а не при отображении.

## Последствия и риски

- Любое изменение состава признаков требует версии схемы `report.schema.json` и обновления рендерера — это намеренная связка с правилом `CONTRIBUTING.md` о версионировании конвейера.
- Детерминированный PDF требует фиксации шрифтов и запрета автоматических дат/меток внутри рендеринга, иначе побайтовое сравнение в тестах станет нестабильным.
- Локализация RU с готовностью к EN означает, что в JSON хранятся коды и значения, а не переведённые строки; перевод происходит только на слое представления.
- Ручные комментарии врача попадают в экспорт — при обезличенном варианте они требуют отдельного предупреждения, поскольку свободный текст может содержать PHI, введённую вручную.

## План проверки

- Golden-тесты: фиксированный вход и model package дают побайтово идентичный JSON; расхождение — регрессия.
- Тест соответствия схеме: любой отчёт валидируется против `report.schema.json` в CI.
- Тест ролей: обезличенный экспорт не содержит ни одного поля из списка идентифицирующих (автоматическая проверка, а не ручной осмотр).
- Тест отказа: при непройденном QC отчёт формируется и явно содержит причину отказа вместо вероятностей.
- Usability-проверка с врачами (M6): понятно ли, что относится к исходным данным, что к расчёту, а что к ручному комментарию.

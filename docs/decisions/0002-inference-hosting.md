# ADR 0002: In-process ONNX Runtime против изолированного локального worker

- Статус: proposed
- Дата: 2026-09-02
- Владельцы: инженерная команда

## Контекст

`docs/architecture/README.md` задаёт рекомендуемый путь реализации: сначала in-process ONNX Runtime за интерфейсом `IInferenceEngine`, при необходимости изоляции GPU/нативных зависимостей — локальный worker с именованными каналами. Нужно зафиксировать это как решение и назвать условия перехода ко второму варианту, чтобы выбор не пересматривался стихийно при первой же native-ошибке.

Ограничения из `docs/windows/README.md`: CPU-only режим обязателен, отсутствие GPU не является ошибкой, анализ должен быть отменяемым, сообщать прогресс и иметь таймаут, падение модели не должно завершать UI-процесс или оставлять незашифрованные временные данные.

## Решение

Для MVP — **in-process ONNX Runtime** внутри слоя `Inference`, скрытый за доменным интерфейсом `IInferenceEngine`. Никакой код за пределами `Inference` не ссылается на типы ONNX Runtime.

Обязательные условия реализации:

- инференс выполняется вне UI-потока, с `CancellationToken` и таймаутом на уровне сценария `Application`;
- выбор execution provider (CPU / GPU) — конфигурация уровня установки, а не жёстко зашитый код; отсутствие GPU-провайдера приводит к предсказуемому откату на CPU с записью в аудит, а не к ошибке;
- рабочие временные файлы создаются в защищённом каталоге и очищаются в `finally` — на успехе, ошибке и отмене;
- интерфейс `IInferenceEngine` проектируется так, чтобы вынос в отдельный процесс не менял его контракт (никаких утечек in-process-семантики вроде передачи указателей или разделяемых мутабельных буферов).

## Рассмотренные варианты

- **Сразу изолированный локальный worker (named pipes)** — отклонено для MVP: добавляет протокол IPC, управление жизненным циклом процесса и сериализацию объёмов до того, как появилась подтверждённая необходимость; замедляет M1–M3 без выигрыша по функциональности.
- **Удалённый inference-сервис** — отклонено: противоречит принципу офлайн-обработки и требует отдельного анализа PHI, угроз и регуляторных требований (`docs/architecture/README.md`).
- **Встроенный Python-рантайм для инференса** — отклонено: тянет Python-зависимость в клиническую поставку, усложняет подписанный установщик и SBOM; Python остаётся только в обучающем контуре `ml/`.

## Последствия и риски

- Нативный сбой в ONNX Runtime или GPU-драйвере может уронить весь процесс приложения — это принимаемый на MVP риск, снижаемый таймаутами и тем, что несохранённое состояние врача минимально.
- Нативные зависимости ONNX Runtime попадают в установщик и SBOM, требуют регулярного сканирования уязвимостей.
- Триггеры перехода к варианту с отдельным процессом фиксируются заранее: воспроизводимые падения процесса из-за GPU-драйвера, необходимость запускать несовместимые версии нативных библиотек одновременно, либо требование ограничить права процесса инференса. При срабатывании любого — новый ADR, заменяющий этот.

## План проверки

- Тест на отмену: длительный анализ прерывается по `CancellationToken`, временные файлы удалены, UI остаётся отзывчивым.
- Тест на ошибку: повреждённый/несовместимый model package даёт понятную ошибку сценария, а не необработанное нативное исключение.
- Тест CPU-only: на машине без GPU анализ проходит, в аудите зафиксирован фактический execution provider.
- Воспроизводимость: один и тот же вход и model package дают идентичный результат (`docs/windows/README.md`).

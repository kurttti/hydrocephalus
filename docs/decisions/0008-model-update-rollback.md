# ADR 0008: Стратегия обновления model package и rollback

- Статус: proposed
- Дата: 2026-09-02
- Владельцы: инженерная команда, релиз-инженер, клиническая команда

## Контекст

ADR 0004 определяет формат пакета, подпись и проверки при загрузке, но не отвечает на вопрос, **как новая модель попадает на офлайн-машину в клинике, кто это разрешает и как вернуться назад**. Требования: `docs/windows/README.md` — model package поставляется отдельно от приложения, обновление модели не должно происходить незаметно, пользователь видит версию, совместимость, источник и статус подписи; M6 в `docs/roadmap.md` — offline deployment и rollback; `docs/security/README.md` — подмена модели как отдельная угроза.

Клиническое обстоятельство: смена версии модели меняет результаты для одного и того же пациента. Это не рядовое обновление ПО, а изменение измерительного инструмента, уже применённого к реальным случаям.

## Решение

**Доставка — только ручная, офлайн.** Приложение никогда не скачивает model package само: нет фонового апдейтера, нет проверки обновлений по сети (`docs/security/README.md`: офлайн по умолчанию, сетевые интеграции отключены до явной настройки администратором). Пакет переносится администратором как файл.

**Установка — явное действие администратора** на экране администрирования: выбор файла → проверки ADR 0004 (схема, подпись, хеши, состав, совместимость версий) → показ версии, идентификатора ключа, статуса подписи, model card и списка отличий от текущей версии → подтверждение → активация.

**Модель сосуществования версий:** установленные пакеты хранятся рядом, помеченные версией; ровно один помечен активным. Установка нового пакета **не удаляет предыдущий**. Rollback = переключение активной метки на предыдущую версию, без переустановки файла и без сети.

**Правила, защищающие клиническую корректность:**

- переключение версии запрещено во время выполняющегося анализа;
- каждый отчёт содержит версию пакета, которой он был получен (ADR 0005), и остаётся неизменным при последующей смене модели — старые отчёты никогда не пересчитываются задним числом;
- смена активной версии, установка и rollback пишутся в аудит с указанием пользователя, времени, версии «из» и «в»;
- если активный пакет несовместим с обновлённым приложением, приложение не подставляет молча другой пакет: анализ блокируется с явным сообщением до решения администратора;
- удаление старой версии — отдельное явное действие, недоступное, пока на неё ссылаются незакрытые случаи в пределах срока хранения.

**Разделение обновлений приложения и модели:** установщик приложения не приносит и не активирует model package. Совместимость проверяется в обе стороны через `manifest.json` (минимальная версия приложения) и через объявленный приложением диапазон поддерживаемых версий схем.

## Рассмотренные варианты

- **Автоматическое обновление модели по сети** — отклонено: противоречит офлайн-режиму и означает незаметную смену измерительного инструмента; прямо запрещено требованием `docs/windows/README.md`.
- **Модель внутри установщика приложения** — отклонено: связывает цикл валидации модели с циклом релиза UI, делает невозможным rollback модели без отката всего приложения и противоречит требованию отдельной поставки.
- **Хранение только одной версии с переустановкой для отката** — отклонено: rollback в клинике должен быть быстрым и не зависеть от того, сохранил ли администратор старый файл.
- **Автоматический откат при ошибке инференса** — отклонено: молчаливая смена версии модели недопустима; сбой должен приводить к отказу и уведомлению, а решение о rollback принимает человек.
- **Пересчёт прошлых отчётов на новой версии** — отклонено: отчёт фиксирует то, что видел врач в момент решения; ретроспективный пересчёт создаёт расхождение с медицинской документацией.

## Последствия и риски

- Ручная доставка означает, что критическое исправление модели распространяется медленно и зависит от организационного процесса — это осознанный компромисс в пользу контролируемости; процедура срочного отзыва версии описывается в эксплуатационных инструкциях M6.
- Хранение нескольких пакетов увеличивает занимаемое место — ограничивается настраиваемым числом хранимых версий, но не менее одной предыдущей.
- Отсутствие сетевой проверки отзыва подписи (унаследовано из ADR 0004) означает, что скомпрометированный ключ нейтрализуется только обновлением приложения.
- Требуется, чтобы UI различал «версия приложения» и «версия модели» так, чтобы врач не путал их при обращении в поддержку.

## План проверки

- Тест установки: корректный пакет активируется только после явного подтверждения; отказ на любой проверке ADR 0004 не меняет активную версию.
- Тест rollback: переключение на предыдущую версию проходит офлайн, без файла-источника, и фиксируется в аудите.
- Тест блокировки: попытка сменить версию во время анализа отклоняется.
- Тест несовместимости: приложение с обновлённой схемой и старым активным пакетом блокирует анализ с явным сообщением, а не подставляет другой пакет.
- Тест неизменности отчётов: отчёт, созданный на версии N, после активации N+1 остаётся побайтово прежним и продолжает указывать версию N.
- Проверка отсутствия сетевой активности при работе с моделями (сетевой монитор в тестовой среде).

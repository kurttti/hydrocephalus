# ADR 0004: Формат model package и подпись

- Статус: proposed
- Дата: 2026-09-02
- Владельцы: инженерная команда, ML-команда, релиз-инженер

## Контекст

Структура model package уже описана в `docs/architecture/README.md` (`manifest.json`, `segmentation.onnx`, `classifier.onnx`, `preprocessing.json`, `features.schema.json`, `labels.json`, `calibration.json`, `model-card.md`, `checksums.sha256`). Не зафиксировано главное: в каком виде пакет поставляется, как подписывается и что именно приложение обязано проверить до загрузки.

Требования: `docs/security/README.md` называет подмену модели отдельной угрозой с мерой «подпись, SHA-256, manifest совместимости»; `docs/windows/README.md` требует, чтобы model package поставлялся **отдельно от приложения** и чтобы обновление модели не происходило незаметно — пользователь видит версию, совместимость, источник и статус подписи.

## Решение

**Формат поставки:** один ZIP-архив с расширением `.hcmp` (hydrocephalus model package), содержащий описанную в архитектуре структуру без вложенных архивов. Внутри — только перечисленные файлы; неизвестные файлы в корне пакета являются причиной отказа загрузки, а не игнорируются.

**Целостность:** `checksums.sha256` покрывает **все** файлы пакета, кроме себя и файла подписи.

**Подпись:** отделённая (detached) подпись файла `checksums.sha256` алгоритмом **ECDSA P-256 + SHA-256**, файл `checksums.sha256.sig`, в паре с идентификатором ключа в `manifest.json`. Открытый ключ поставляется вместе с приложением (в подписанном Authenticode установщике), а не берётся из самого пакета.

**Порядок проверки при загрузке — строго до чтения любых весов:**

1. схема `manifest.json` валидна;
2. подпись `checksums.sha256` проверена доверенным открытым ключом;
3. хеши всех файлов совпадают с `checksums.sha256`, состав файлов совпадает ровно;
4. `manifest.json` объявляет минимальную версию приложения, и текущая версия ей удовлетворяет;
5. версии `preprocessing.json`, `features.schema.json` и `labels.json` совместимы с тем, что умеет `Inference`.

Любой отказ на шагах 1–5 — это отказ загрузки с машинно-читаемым кодом и человекочитаемым объяснением; частичная загрузка запрещена. Факт загрузки, версия пакета, идентификатор ключа и статус подписи пишутся в аудит и отображаются в UI администрирования.

**Ключи:** приватный ключ подписи модели хранится вне репозитория и вне машин разработки (аппаратный токен или managed KMS релиз-контура), отдельно от ключа Authenticode для установщика — компрометация одного не даёт подменить другое.

## Рассмотренные варианты

- **Подпись каждого файла отдельно** — отклонено: не защищает от удаления/добавления файлов и усложняет ротацию ключей; подпись манифеста хешей закрывает и состав, и содержимое.
- **Только SHA-256 без подписи** — отклонено: защищает от повреждения, но не от целенаправленной подмены; прямо противоречит мере из `docs/security/README.md`.
- **Authenticode-подпись пакета как исполняемого артефакта** — отклонено: Authenticode рассчитан на PE-файлы, а не на архивы данных; остаётся только для установщика приложения.
- **GPG/OpenPGP** — отклонено: тянет внешнюю зависимость и модель доверия к кольцам ключей, избыточную для одного издателя.
- **RSA-4096 вместо ECDSA P-256** — рассмотрено как равнодопустимое; ECDSA выбран за компактность подписи и наличие в .NET без сторонних библиотек. Смена алгоритма — новый ADR.
- **Хранение классификатора в pickle/joblib** — отклонено: небезопасная десериализация; либо ONNX, либо строго версионированный артефакт с явной схемой, как и записано в архитектуре.

## Последствия и риски

- Требуется процесс управления ключами и их ротации до первой пилотной поставки; ротация ключа означает выпуск обновления приложения с новым доверенным ключом — это учитывается в графике релизов.
- Строгая проверка состава пакета сделает невозможной «горячую» подкладку файлов в каталог модели — это намеренно.
- Классификатор не всегда экспортируем в ONNX без потери поведения (например, отдельные реализации градиентного бустинга) — в таком случае в пакете лежит версионированный артефакт с собственной схемой, и требование «никакой произвольной десериализации» остаётся в силе.
- Отсутствие сети означает отсутствие проверки отзыва ключа онлайн: отзыв доводится обновлением приложения, что закладывает задержку реакции.

## План проверки

- Тесты загрузки: корректный пакет; изменённый байт в весах; удалённый файл; добавленный лишний файл; неверная подпись; подпись неизвестным ключом; несовместимая минимальная версия приложения — каждый случай даёт свой код отказа.
- Тест аудита: после успешной и неуспешной загрузки в журнале есть версия пакета, идентификатор ключа и статус подписи.
- Утилита `tools/` проверяет пакет вне приложения (`--help`, машинно-читаемый код возврата) и используется в релизном пайплайне.
- Проверка, что приватный ключ отсутствует в репозитории и в артефактах сборки (secret scanning в CI).
